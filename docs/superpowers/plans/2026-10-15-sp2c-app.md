# SP2c — The application: the `host` crate and the Tauri interface — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a version of inkemu driven entirely from a graphical interface (the user's rule "Interface first"): the host policy of `emu-cli` moved into a library crate the CLI consumes unchanged, a machine that runs on its own thread and takes commands, two ports for the panel image and the buttons with a test pattern until SP2d, and a Tauri 2 application that calls that crate and holds no logic.

**Architecture:**

| Where | Owns | Why |
|---|---|---|
| `crates/host` (moved modules) | `term`, `exit`, `flash_file`, `flash_state`, `firmware_file`, `script_file`, `session_file`, `record`, `run`, `rom_store` | the host policy of `inkemu run`, now shared (C1) |
| `crates/host/src/launch.rs` | the console shown and its note, the header, the flash note, the starting flash, the refusals of paths, the ROM | what `main.rs` decided (C1) |
| `crates/host/src/{ports,pattern,catalog}.rs` | `PanelSource`, `ButtonPort`, the test pattern, the ports of each profile | the contract SP2d plugs into (C8, spec §4) |
| `crates/host/src/{utf8,capture}.rs` | streamed UTF-8, PNG of a panel image | C12, C13 |
| `crates/host/src/engine.rs` | one life of a machine, without host I/O | C3, C5, C7, C9, C10 |
| `crates/host/src/device.rs` | the thread, its commands, pacing, lives, flash file, sessions | C3, C4, C6, C10, C14 |
| `crates/emu-cli` | clap, Ctrl-C, the reader of standard output, `inspect`, `rvtest` | a thin front end |
| `app/` | React + Vite + TypeScript 7 interface; `app/src-tauri` the Tauri 2 shell (own workspace) | C11, C15–C17 |
| `.github/workflows/ci.yml` | job `app` | C18 |

**Tech Stack:** Rust 1.99.0 (edition 2024); Tauri 2.12.4, tauri-build 2.7.3, tauri-plugin-dialog 2.8.3; Node 24; pnpm 12.11.2; Vite 8.3.4; TypeScript 7.0.2; React 19.3.1; Vitest 5.0.4 + jsdom 30 + Testing Library; Biome 2.5.15. Sources: `docs/research/sp2c-app-stack.md`.

**Spec:** `docs/superpowers/specs/2026-10-15-sp2c-app-design.md` (decisions C1–C18, binding). ADR 0011.

## Global Constraints

- `crates/soc-esp32c3` and `crates/chips` are not touched (other sub-projects work there).
- No output or exit code of `inkemu` changes; no test of `crates/emu-cli/tests` is edited to follow the move.
- Sources are edited with Edit/Write only; files are moved with `git mv` (bytes unchanged), then edited.
- No secret, no TODO, no trailer in commits; commits `type(scope): description`; nothing is pushed.
- Local checks only: `cargo fmt`, clippy on `host`, `emu-cli` and the shell, the tests of `host` and `emu-cli`, the front's checks; the Tauri bundle at most once. `CARGO_BUILD_JOBS=3`.

## Rulings taken while doing it

| # | Ruling | Why |
|---|---|---|
| 2c-R1 | **Move, then re-export.** `emu_cli::{term, exit, flash_file, …}` stay valid paths through `pub use host::…`; the integration tests of `emu-cli` compile untouched. The unit tests of each moved module move with it. | No regression is provable only if the tests are the same. |
| 2c-R2 | **`pub(crate)` items the CLI used across modules become `pub`** in `host` (`read_regular_file`, `ReadFailure`, `same_file`, `temporary_path`, `journal_prefix`, the summary of `run`): they cross a crate boundary now. Nothing else of their visibility changes. | The smallest change that compiles. |
| 2c-R3 | **`StartError`** wraps `FlashFileError` and `FirmwareFileError` and displays as they do: `main.rs` prints `error: {e}` as before. | Same bytes on standard error. |
| 2c-R4 | **The machine is built on the thread** by a `Recipe` (`Send`); `Esp32C3`, the ports and the engine never cross threads. | `Esp32C3: !Send` (C3). |
| 2c-R5 | **A command is answered after the worker handled it**, between two passes (`Emulator::command` blocks on a reply channel). A command sent to a stopped worker is `CommandError::Stopped`. | A caller learns a refusal from the call that caused it. |
| 2c-R6 | **Status is sent at most every 100 ms of host time**, and at once on a change of state. Console text and notices are sent after the pass that produced them. | Ordered, bounded traffic (C11). |
| 2c-R7 | **Pacing**: in real time, the pass's device-time bound is `base_device + elapsed_wall`, reset when the run starts, resumes, changes speed or a life begins; the worker waits up to 5 ms on its command channel when the machine caught up. | No sleep that delays a command. |
| 2c-R8 | **A halt (C5) is left on any accepted input or a reset**; a step while halted is refused (`NothingToRun`). | The machine would return the same halt at once. |
| 2c-R9 | **`Stop` ends the last life**: flash file written, session written, the summary lines of `run` sent as notices, then `Update::Ended`; the thread ends. | One place where a life ends, whatever ends it. |
| 2c-R10 | **The front's state is a reducer of `Update`s**; it decides nothing about the device: every enabled control follows the state `host` sent. | No business logic in TypeScript (C15). |
| 2c-R11 | **The front's files are named in kebab-case** (`device-view.tsx`), components keep PascalCase names inside. | A check of the development host refuses other TypeScript file names. |
| 2c-R12 | **A `Handle` (cloneable) commands the emulator**: the Tauri shell clones it under its lock and waits for the answer off the lock and off the main thread (`spawn_blocking`). | A command waits for the end of a pass; nothing else must wait behind it. |
| 2c-R13 | **The flash is never lost on a failure path**: a power-on that fails gives its content back (`FlashKeeper::abandon`); a flash file that cannot be written keeps the content in memory, which replaces the file at the end of the next life. Found by the review during the work, each with its test. | Zero loss of what the firmware wrote. |
| 2c-R14 | **The controls are a labelled region, not an ARIA toolbar**: they hold selects, which take the arrow keys a toolbar uses to move; Tab moves between controls. The device itself is `role="application"`: it takes its own keys while it has the focus. | An ARIA role promises a keyboard behaviour. |
