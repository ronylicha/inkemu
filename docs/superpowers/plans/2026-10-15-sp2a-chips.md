# SP2a — The external chips of the X4 — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a crate `crates/chips` that depends on `emu-core` only, knows no `SoC`, builds for `wasm32-unknown-unknown` and performs no host I/O, holding the SSD1677 e-paper controller of the X4 as a complete command interpreter with an optical model of the panel, the button ladders and the battery the SAR ADC reads. SP2d wires them to the pins of the X4; SP2b models the `SoC` peripherals they hang on; SP2c shows the panel.

**Tech Stack:** Rust 1.99.0 (edition 2024). No new package: `emu-core` and `thiserror`, both already in the workspace.

**Spec:** `docs/superpowers/specs/2026-10-15-sp2a-chips-design.md` (decisions A1–A17, binding). Research: `docs/research/sp2a-external-chips.md` (the SSD1677 datasheet Rev 1.0, pinned by its SHA-256 and not stored; `FreeInk` at the commit `CrossPoint` pins; `CrossPoint`; Papyrix).

**What was verified, and where.** On the development host, with `CARGO_BUILD_JOBS=3` (the host is shared): `cargo fmt --all --check`; `tools/ci/clippy.sh -p chips --all-targets --all-features -- -D warnings`; `cargo doc -p chips --no-deps --document-private-items` with `RUSTDOCFLAGS=-D warnings`; `cargo test -p chips` (79 unit tests, 8 integration tests); `cargo check --target wasm32-unknown-unknown -p chips`; `cargo test -p boards --test host_io_ban` (3 tests, seven copies); `cargo test -p inkemu-lockstep --test readme` (the README changed). **Not run on that host**, left to the CI: `cargo test --workspace`, clippy and rustdoc on the whole workspace, coverage, the ignored suites.

## Global Constraints

- `chips` depends on `emu-core` and `thiserror` only; no `SoC`, no host I/O, no host clock, no thread; it builds for `wasm32-unknown-unknown`.
- Time is device time, cycles of the machine's time base, passed with every call; nothing is computed from host time.
- Every value no source gives is a parameter or an `ASSUMPTION:` in the code, listed in the research report (§5).
- No third-party binary in the repository: the datasheet is cited by URL and SHA-256.
- Commits: `type(scope): description`, no trailer.

## Rulings taken while doing it

| # | Ruling | Why |
|---|---|---|
| 2a-R1 | **The crate boundary.** `chips` holds the chips; their wiring to pins, to GP-SPI2 and to the SAR ADC is SP2d's; the ADC's conversion of a voltage to a code is SP2b's. `crates/chips/clippy.toml` is the seventh copy of the ban; `host_io_ban.rs` lists `chips`; the comment of every copy names it. | Spec §3.2: the external chips see signals, never the `SoC`. |
| 2a-R2 | **Bytes, not bits.** `write_command(now, byte)`, `write_data(now, byte)`, `read_data(now) -> Option<u8>`, `set_reset(now, asserted)`. A read with nothing driven gives `None`: the line floats and the board decides its level (the X4-family probe expects that). | The SPI framing, D/C# and CS# belong to the adapter (A1). |
| 2a-R3 | **Called back, never polled.** `next_deadline()` is the next instant BUSY falls or an image is published; `advance(now)` brings the chip there; every call advances first. An instant before the latest seen counts as the latest. | ADR 0003, point 3; `FreeInk` waits on BUSY edges by interrupt (A2). |
| 2a-R4 | **Durations in nanoseconds, converted once** by `Frequency::nanos_to_cycles` (rounded up), from `Ssd1677Timing`; defaults sourced or marked (research §5): analog on 100 ms and off 200 ms (Papyrix), the rest assumptions kept below what the firmwares wait. | A3, A13. |
| 2a-R5 | **A command during BUSY is dropped with its data and reported, except `0x2F`**, executed; in deep sleep everything is dropped until a hardware reset; while RES# is low everything is dropped and BUSY reads low. | A6; the status's busy bit needs to be readable while busy. |
| 2a-R6 | **Every command of Table 7-1 has a named treatment**, held by a test that lists the datasheet's codes: modelled, `UnsupportedCommand` (OTP programming and load, CRC, initial code, external sensor command, dithering), `ReservedCommand` (`3A`, `3B`); any other byte is `UnknownCommand`. | A4. |
| 2a-R7 | **Diagnostics are bounded** (1 024 waiting, the rest counted) and reported once per command, never per data byte. | A firmware cannot grow the queue without end. |
| 2a-R8 | **RAM addressing.** X is a source address; a byte covers eight sources, the most significant bit leftmost; the counter steps one byte in X, one row in Y, wraps to the window's start past its end in the data-entry direction, and the other axis steps; a counter past the RAM writes nothing (reported once per command); a counter outside the window at the start of a RAM command is reported. | A7; `FreeInk` writes X in pixels and 100 bytes per row. |
| 2a-R9 | **`0x46` fills RED and `0x47` B/W**, as the datasheet says; `FreeInk` and Papyrix name them the other way round, which `F7` to both hides. The fill covers the whole RAM. | The datasheet is the chip's own document. |
| 2a-R10 | **`0x22`, one bit per stage**, run by `0x20` in the order clock, analog, temperature, LUT, display, analog off, clock off; a stage whose supply is off is skipped and reported; no waveform for the temperature skips the display (reported). | A8; the datasheet's combinations agree with the bit reading. |
| 2a-R11 | **The OTP is a parameter**; the GDEQ0426T82's three reference settings (`reference::gdeq0426t82_otp`) reproduce 1.8 s full, 0.5 s fast, 1.7 s half with the default stage durations; the last matching setting wins, lower bound excluded. | A9; datasheet §6.9. |
| 2a-R12 | **The optical model is integer and composed.** A pixel's state lies in `[0, swing]` (mV·ns); a phase is a clamped translation by (source − VCOM swing) × time, negated when a positive voltage darkens; a waveform composes into one translation per LUT, so a refresh costs one evaluation per pixel whatever its repeats. **DCVCOM drives no pixel** (decided while writing the tests: with it, VSS phases moved every pixel, which the X4's grey LUT contradicts; research §6). | A10. |
| 2a-R13 | **Frame-rate codes**: byte 100 + *k* holds group 2*k* in its high nibble; each code's period is a parameter, 20 ms by default. | The datasheet does not describe the five bytes. |
| 2a-R14 | **`RefreshKind` follows the display mode**: 1 is `Full`, 2 `Partial`; the image is published at the end of the display stage, before the analog-off stage; a hardware reset during the display publishes the state reached at that instant (`interrupted`), whole frames only. | A11. |
| 2a-R15 | **Deep sleep**: `11` loses the RAM (cleared to 0), `01` and `10` are reported and keep it, extra bits are reported; BUSY stays high, `next_deadline` is `None`. | A6; `FreeInk`: mode 2 discards the RAM. |
| 2a-R16 | **`0x1A` takes one or two bytes** without a diagnostic, `A[3:0]` kept when the second is missing; `0x21` takes a second byte, stored only. | A17: the X4's half refresh sends one byte. |
| 2a-R17 | **Reads**: `0x27` gives a dummy byte, then the RAM at the counter, which advances (Table 7-1, against §8.5); `0x1B`, `0x2D`, `0x2E`, `0x2F` give their registers; reading after a write command gives `None`, reported once. | The command table is the more specific of the two. |
| 2a-R18 | **The border** follows a LUT (`0x3C` = 00b), a fixed level (01b) through the VCOM phases, or nothing (VCOM, HiZ); it is part of `PanelImage`. | Datasheet `0x3C`. |
| 2a-R19 | **The booster soft-start (`0x0C`) and the VCOM glitch control (`0x2B`) are accepted without effect**, not stored. | The model has no currents or edges to shape. |
| 2a-R20 | **The geometry is a parameter**: width, height, first source, reversed columns, the native gate scan (SM, GD) and reversed rows; the gates are the panel's rows through Table 8-2; a native GD = 1 needs an even height. The X4: 800×480, SM = 1, rows reversed. | A12. |
| 2a-R21 | **Ladders and batteries speak millivolts at the pin.** Several keys held read the lowest level (a series ladder, assumption); a divider rounds half up, computed in `u128`. | A14, A15: the code depends on the attenuation the firmware chose. |
| 2a-R22 | **Tests.** Unit tests on a 32×4 panel (quick displays), one per command and per mode plus the edge cases; integration tests through the public interface on the 800×480 panel with `FreeInk`'s exact byte sequences and the waits a firmware makes. | Criteria 1 and 2 of the spec. |
| 2a-R23 | **CI**: `-p chips` joins the WebAssembly step; the other steps take the crate through `--workspace`. | Minimal change. |
