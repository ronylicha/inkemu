# SP1b-4e — CoreMark dans ±15 % du score publié : design

Date : 2026-10-15. Spec globale : `docs/superpowers/specs/2026-10-11-inkemu-design.md` §1 (points 2 et 4), §4.2
(« un test automatique exécute CoreMark et vérifie que le score émulé reste dans ±15 % du score publié pour
l'ESP32-C3 »), §8, §10.2 point 11, §10.3 critère 5. Découpage : `docs/superpowers/notes/2026-10-14-sp1b-4-decoupage.md`.
Héritage : `docs/superpowers/notes/2026-10-14-sp1b-4d-carryover.md` (« Laissé aux héritiers »), ADR 0008,
`docs/lockstep-differences.md`. Recherche : `docs/research/coremark-esp32c3.md` (CM ci-dessous),
`docs/research/sp1b-test-oracle.md` §3–§4, `docs/research/sp1b-4-scoping.md` §1(b).

## 1. But

Tenir le critère 5 en CI : l'exemple CoreMark d'Espressif, construit comme les autres firmwares de référence et
démarré par `inkemu run --firmware`, imprime un score, chronométré par le firmware sur le temps d'appareil d'inkemu,
à moins de 15 % du score qu'Espressif publie pour la puce. Trancher les deux reports que SP1b-4d laisse à ses
héritiers : le premier tick que QEMU prend deux instructions après inkemu, et le `MEIP` de QEMU dans
`usb_serial_jtag_echo`.

## 2. Décisions

| # | Décision | Raison |
|---|---|---|
| K1 | **Le score publié est celui de la fiche technique** : ESP32-C3 Series Datasheet v2.4 (2026-05-06), page 3, « 1 core at 160 MHz: 483.27 CoreMark; 3.02 CoreMark/MHz ». Bande : [410,78 ; 555,76]. Le chiffre de l'exemple `espressif/coremark` (409,25, GCC 12.2) est rapporté par le test et les documents, pas testé. La mesure (K3) tombe dans les deux bandes : le choix ne dépend pas d'elle. | C'est le score de la puce, publié par Espressif, celui que la spec nomme (§1 point 2) ; l'exemple n'est qu'une sortie d'exemple, faite avec un compilateur plus ancien. La fiche ne dit ni compilateur ni options (CM §1). |
| K2 | **Le score mesuré est celui que le firmware imprime**, chronométré par `esp_timer`, c'est-à-dire par le SYSTIMER d'inkemu, qui compte le temps d'appareil ; avec le modèle de temps par défaut (`datasheet-uncalibrated`). Aucun modèle de temps propre au test. | La consigne : le temps d'appareil d'inkemu, la machine que l'utilisateur fait tourner. |
| K3 | **Aucun coût n'est ajusté.** Mesuré le 2026-10-15 : 424,628450 (−12,1 % de 483,27 ; +3,8 % de 409,25), 6000 itérations en 14 130 ms, CRC justes. `is_calibrated()` reste `false`. Un score qui sortirait de la bande après une modification est un défaut du modèle de temps, cherché et corrigé là avec un test ; la bande n'est jamais élargie. | Un seul benchmark donne une équation pour dix coûts de classe : un ajustement serait arbitraire et déplacerait toutes les empreintes de trace épinglées sans gain vérifiable. « Calibré » veut dire mesuré sur un appareil (spec §1 point 4) : le banc du sous-projet 8. ADR 0009. |
| K4 | **Le firmware** est l'exemple et le composant `espressif/coremark` 1.1.0~2, **copiés sans modification** dans `tools/reference-firmware/coremark_example/` (composant dans `components/coremark/`), chaque fichier vérifié contre le `CHECKSUMS.json` du registre ; construit par `build.sh` dans `espressif/idf:v5.5.2`, sans réseau ni gestionnaire de composants ; ses trois binaires épinglés (`SHA256SUMS.inputs-coremark`) ; les fichiers copiés épinglés (`SHA256SUMS.coremark-sources`) et vérifiés par `in-container.sh` avant la construction. Le binaire n'est jamais versionné. | La construction de référence est hors réseau (`--network none`, `IDF_COMPONENT_MANAGER=0`) ; les règles de CoreMark demandent ses fichiers non modifiés. |
| K5 | **Le test** est un test ignoré d'`emu-cli` (`run_cli.rs`, le nom contient `reference_firmware`, job `reference-boot`, effectif 13 → 14) : empreinte du binaire ; code 0 ; **d'abord** le score de la ligne `CoreMark 1.0`, dans la bande de K1 (les deux bornes), dès qu'il est lu, puis le score dans chaque message d'échec ; en-tête, taille 666, IRAM, les quatre CRC indépendants du nombre d'itérations, « Correct operation validated », 160 MHz du firmware, retour d'`app_main` ; aucun `ERROR!` ; l'horloge du CPU d'inkemu à 160 MHz à la fin de l'exécution, endormi ou non (ligne `CPU clock at 160 MHz` de son résumé) ; une table itérations → `crcfinal` dont chaque entrée vient d'une source autre qu'inkemu (6000 → 0xa14c), tout autre nombre d'itérations échouant ; au moins 10 s ; le score égal à `Iterations/Sec` et à itérations × 1000 / ticks ; aucun avertissement ; l'empreinte de trace. | Le critère 5, plus ce qui rend la mesure valide au sens de CoreMark. |
| K6 | **Licence et marque.** Les sources copiées gardent leurs fichiers `LICENSE` ; `PROVENANCE.md` donne l'origine, les empreintes et l'avis de marque ; les deux README le disent. Le `NOTICE` racine, qu'`inkemu licenses` imprime et qui dit ce que le **produit** contient, ne change pas : CoreMark est dans le dépôt, pas dans le produit. Ce qu'imprime le firmware sous inkemu n'est jamais présenté comme un score CoreMark d'un appareil. | Accord d'usage de la marque CoreMark, clauses 1.2 et 2.1 ; Apache-2.0 pour les sources (CM §2). |
| K7 | **Rien d'autre ne change par défaut** : ni la machine, ni les empreintes de trace épinglées (12 s `a0d221296337b295`, 40 000 001 cycles `fb9ea628bc25b355`, `adc_wait_panic` `b217bc3b287080ae`, `deep_sleep_timer` `80bd1c43d55b5467`), ni les fenêtres du lockstep. Aucune logique de produit n'est ajoutée : la CLI et les crates bibliothèques ne changent pas, hors des commentaires de documentation : celui d'`IntMatrix::asserted_as_qemu` (K8 c) et, à la relecture, ceux de `cpu-rv32/src/timing.rs`, réécrits selon l'ADR 0009 (estimations non calibrées, ajustées seulement sur un appareil au sous-projet 8 ; aucune valeur changée). | Contraintes du projet ; interface graphique d'abord (rien à exposer). |
| K8 | **Les reports de SP1b-4d.** (a) **Le tick** : *reporté au sous-projet 8*. Une des deux instructions s'explique par un raisonnement sur le code, non mesuré (QEMU ancre l'alarme sur son horloge virtuelle lue pendant le rangement, que le décompte sous `-icount` fait compter ; inkemu au début du rangement : `esp_systimer.c` lignes 105–154, `icount-common.c` 71–126) ; l'autre n'est pas dans `esp_systimer.c`, et la règle de SP1b-4d n'admet un réglage `QemuCompat` que pour un écart sourcé là. Seule la puce dit où ancrer l'alarme d'inkemu. (b) **Le `MEIP`** : *réfutation établie, cause déduite*. Fait établi : le QEMU épinglé (étiquette `esp-develop-9.2.2-20250817`) n'a pas d'interruption USB-Serial-JTAG, ce qui réfute l'hypothèse de SP1b-4d. Cause proposée : sa matrice garde un bit « en attente » collant et son CPU laisse `MEIP` levé tant qu'elle en rapporte un (CM §6.2) — **déduite du code de QEMU et de l'état à l'arrêt, non observée dans QEMU**. Sa ligne n'est pas ajoutée : une ligne appartient à une fenêtre qui l'utilise (R35, H3), et aucune application composée n'a de fenêtre tant que (a) n'est pas tranché ; *son traitement, et l'observation du bit dans QEMU (moniteur ou gdbstub), sont reportés avec (a) au sous-projet 8*. (c) **La ligne 4** cite la branche `esp-develop` de QEMU, pas l'étiquette que le lockstep fait tourner : sa source est corrigée par une révision datée (tableau, ADR 0008, commentaire de `IntMatrix::asserted_as_qemu`) ; sa mesure et son traitement ne changent pas. | Consigne : trancher chacun ; règles de SP1b-4d (R35, R37, note de passation). |
| K9 | **Pas de comparaison du nombre d'instructions par itération avec QEMU.** | Le critère ne la demande pas ; le lockstep de 2,2 milliards d'instructions prendrait des heures (environ 133 000 instructions/s), et la CLI ne choisit pas le modèle `qemu-icount`. Le lockstep prouve déjà l'égalité instruction par instruction sur ses fenêtres. |
| K10 | Documents : rapport CM, ADR 0009 (le temps de référence), section datée de l'ADR 0008, tableau des différences (révisions datées), README, README des firmwares de référence, note de passation `2026-10-15-sp1b-4e-carryover.md`, cartographie. | Traçabilité. |

## 3. Hors périmètre

- L'ajustement des coûts sur un appareil et le passage à « calibré » (sous-projet 8).
- Le cache de flash et son coût (sous-projet 8) : CoreMark tourne en IRAM et n'y est pas sensible.
- Les fenêtres du lockstep pour les applications composées (après K8 a).

## 4. Critères d'acceptation

1. `tools/reference-firmware/build.sh` construit `coremark_example.bin` à l'empreinte épinglée, après avoir vérifié
   les fichiers copiés ; deux constructions propres donnent les mêmes empreintes.
2. Le test de K5 passe en local et dans le job `reference-boot` ; il échoue quand le modèle de temps sort de la
   bande (vérifié par une mutation, défaite).
3. Les empreintes de trace épinglées et les fenêtres du lockstep sont inchangées ; la CI est verte.
4. Chaque report de SP1b-4d est tranché, avec sa source ou son héritier et sa raison.

## 5. Note du 2026-10-15, après la relecture (I1–I3, M1–M9)

- **K8 reformulée** : ce qui est établi (la réfutation de l'hypothèse USB-Serial-JTAG) est séparé de ce
  qui est déduit (la cause du `MEIP`, une des deux instructions du tick) ; l'observation dans QEMU va au
  sous-projet 8.
- **Sources de QEMU** : la référence est l'étiquette du build épinglé ; les lignes du tableau qui citent
  QEMU sont relues contre elle (ADR 0008, « Révision du 2026-10-15, relecture de SP1b-4e ») ; seules les
  sources des lignes 2 et 4 changent.
- **K5 précisée** (score d'abord, table des `crcfinal`, horloge d'inkemu) ; **K7 précisée**
  (commentaires de `cpu-rv32/src/timing.rs`) ; `in-container.sh` vérifie aussi la liste des fichiers de
  `coremark_example/`. Aucune décision ne change de sens, aucune mesure ni épingle ne change.
